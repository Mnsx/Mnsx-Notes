# 智能指针

C++11提供四种智能指针：`std::auto_ptr`、`std::unique_ptr`、`std::shared_ptr`、`std::weak_ptr`

std::auto_ptr是从C++98残留下来的**废弃特性**，他是一种对智能指针进行标准化的尝试，在C++11中演变成了std::unique_ptr，要正确实现智能指针需要移动语义，但是C++98没有这个语义，于是std::auto_ptr使用它的复制操作来完成移动任务

## unique_ptr作为资源管理器

**std::unique_ptr不允许复制**，因为复制一个std::unique_ptr，就会得到两个指涉相同资源的智能指针，而且两者都会认为自己拥有这个资源，而这两者都认为自已应当析构该资源，所以**std::unique_ptr属于是只移类型**

默认的，析构通过delete运算符实现，但是在析构过程中std::unique_ptr可以被设置为使用自定义析构器：析构资源时所调用的任何函数（或函数对象）

```c++
auto customDeleter = [](Pointer * p) {
    
    log();
    delete p;
}; // 自定义析构器的Lambda表达式

template <typename T>
std::unique_ptr<Pointer, decltype(customDeleter)> getPointer(T && params) {
    
    std::unique_ptr<Pointer, decltype(customDeleter)> p(nullptr, customerDeleter);
    
    // 根据创建的类型填写实例
    if (...) {
        
        p.reset(new ...);
    }
    
    return p;
}
```

因为直接将一个裸指针赋值给std::unique_ptr，会发生从裸指针到智能指针的隐式类型转换，而这种转换存在很大的问题，所以C++11中直接禁止了这种行为，**需要通过reset来指定让智能指针获取使用new产生的对象的所有权**

使用默认析构函数的前提下可以认为std::unique_ptr与裸指针尺寸相同，但是如果使用了自定义析构器后，如果析构器是函数指针，**那么std::unique_ptr的尺寸一般会增加一到两个字长**，如果是函数对象，**则带来的尺寸变化取决于该函数存储了多少成员变量**，而无捕获的Lambda表达式不会浪费任何存储尺寸，使用它就是最优解

std::unique_ptr以两种形式提供，一种是单个对象，一种是数组（std::unique_ptr<T[]>），这样就不会引起二义性，并且API也与类型相匹配，如单个对象无法使用索引运算符，而数组形式无法使用提领运算符

std::unique还有一个很好的特性，**它可以方便高效的转换成std::shared_ptr**

```c++
std::shared_ptr<Investment> sp = getPointer(...); // 隐式转换
```

## shared_ptr管理共享资源

通过std::shared_ptr这种智能指针访问的对象采用共享所有权来管理其生存期，**当最后一个指涉到某对象的std::shared_ptr不再指涉到它时，该std::shared_ptr会析构其指涉到的对象**

std::shared_ptr可以通过访问某资源的引用计数来确认是否时最后一个指涉到该资源的，**引用计数是个与资源关联的值，用来记录跟踪指涉到该资源的std::shared_ptr数量**

引用计数的存在会带来性能影响：

* **std::shared_ptr的尺寸是裸指针的两倍**，因为它们内部即包含一个指涉到该资源的裸指针，还包含一个指涉到该资源的引用计数的裸指针
* **引用计数的内存必须动态分配**
* **引用计数的递增和递减必须是原子操作**，因为在不同的线程中可能存在并发的读写器，原子操作一般比非原子操作慢，所以即使引用计数通常只有一个字长，也应当假设它们的读写成本非常高昂

**从一个已有std::shared_ptr移动构造一个新的会将原本的std::shared_ptr置空**，这意味着一旦新的std::shared_ptr产生后，原有的将不会指涉其资源，因此移动比赋值更快

std::shared_ptr也同样可以自定义析构器

```c++
auto customDeleter1 = [](Widget * pw) {...};
auto customDeleter2 = [](Widget * pw) {...};

std::shared_ptr(Wdget) pw1(new Widget, customDeleter1);
std::shared_ptr(Wdget) pw2(new Widget, customDeleter2);
```

而由于pw1和pw2具有同一类型，所以他们可以放到一个容器中，可以相互赋值，可以被传递到要求std::shared_ptr<Widget>类型的形参中，而这些对于具有不同自定义析构器类型的std::unqie_ptr是不能做到的

和std::unqie_str的另一个不同在于，自定义构造器并不会改变std::shared_ptr的尺寸，**无论析构器的类型，std::shared_ptr对象的尺寸都相当于裸指针的两倍**

这个功能的实现原理在于std::shared_ptr将析构器的存储内存放在了堆上，std::shared_ptr对象包含了指涉到一个它所指向的对象引用计数的指针，而该引用计数是控制块的一部分，在这个控制块中同时还包含了自定义析构器的一个复制，这个控制块中可能还包含其他附加数据

一个对象的控制块由创建首个指涉到该对象的std::shared_ptr的函数来确定，到那时正在创建指涉到某对象的std::shared_ptr无法获知是福哦已经有指涉该对象的存在，所以控制块的创建遵照一下规则

* **std::make_shared总是创建一个控制块**

  std::make_shared会产生新的对象，并且使用std::shared_ptr指向这个新对象，所以不会存在这个对象已经被指涉的情况

* **从具备所有权的指针构造std::shread_ptr时，会创建一个控制块**

  专属所有权的智能指针不适用控制块，因此不应该存在所指涉的对象存在控制块的情况

* **当std::shared_ptr构造函数使用裸指针作为实参调用时，会创建一个控制块**

  这条规则可能导致同一个对象拥有多个控制块，被析构多次，**尽可能避免将裸指针作为实参传递给一个std::shared_ptr的构造函数**

## 空悬指针使用weak_ptr

std::weak_ptr一般通过std::shared_ptr来创建的，当使用std::shared_ptr完成初始化std::weak_ptr的时候，两者就指涉到相同位置，但是std::weak_ptr并不影响所指涉到的对象的引用计数

std::weak_ptr的空悬，也被称为失效

```c++
if (wpw.expired()) {...}
```

由于std::weak_ptr缺乏提领操作，所以无法主动将它指涉到一个对象地址，**但是可以通过将指涉新对象的std::shread_ptr赋值给它来实现**

这又会引导出新的问题，因为这个操作将检验和提领分离开来了，所以可能会带来竞争风险，在expired的调用和提领操作之间，可能另一个线程会重新赋值或析构最后一个指涉到该对象的std::shared_ptr，从而导致该对象析构，这种情况下提领就会产生问题

解决这个问题的方法就是使用原子操作来完成std::weak_ptr是否失效的校验，以及在未失效的条件下提供对所指涉到的对象的访问，实现这个有两种方式，使用那种方式取决于如果std::weak_ptr创建std::shared_ptr失效时，所期望的结果

* 第一种通过`std::weak_ptr::lock`，它返回一个std::shared_ptr，如果已经失效那么这个std::shared_ptr就为空
* 第二种通过使用std::weak_ptr作为实参来构造std::shared_ptr，如果已经失效，那么就会直接抛出错误

> std::shread_ptr已经有引用计数了为什么还需要std::weak_ptr?
>
> **引用计数是提供给资源持有者看的，而不是调用者**
>
> 如果资源已经全部被清除了，std::shared_ptr都已经被清除了，是无法查看引用计数的，智能通过std::weak_ptr来判断是否已经被清除

## 优先使用make而不是new

`std::make_shared`是C++11的一部分，而`std::make_unique`是C++14才引用的内容

```c++
template <typename T, typename ... Ts>
std::unique_ptr<T> make_unique(Ts && ... params) {
    
    return std::unique_ptr<T>(new T(std::forward<Ts>(params)...));
}
```

make产生的智能指针相比于new产生的，除了代码简略之外，还能保证**异常的安全性问题**

由于编译器从源代码到目标代码翻译过程中，产生的代码不一定和所期望顺序相同的代码，所以可能会导致资源泄露的问题

```c++
int computePriority();

processWidget(std::shared_ptr<Widget>(new Widget), computePriority());
```

就比如上述代码，正常期望的顺序应该是，先在堆上创建一个Widget对象，然后由new产生裸指针指向对象的地址，然后将这个new产生的对象地址，交给托管对象std::shared_ptr，最后执行computePriority函数

但是由于**编译器的指令重排机制**，可能导致computePriority函数在任何位置被调用，这就意味着如果new之后调用computePriority，但是这个函数抛出了异常，那么这个对象地址就泄露了

而使用make_shared就可以完全避免这个问题

使用make的原因还有是因为性能的提升，使用new需要进行两次内存分配，第一次是分配所指涉对象的内存，第二次是分配控制块的内存，**而使用make则是直接分配单块内存，将两个数据同时保存**

同样存在不应该使用make函数的情况

* **所有make函数都不允许使用自定义析构器**

* **需要使用初始化列表来创建指涉到对象的指针时不能使用make**

  使用初始化列表时，代码优先选择std::initiallizer_list类型的形参来重载构造函数

  ```c++
  auto upv = std::make_unique<std::vector<int>>(10, 20);
  ```

  那么下面的情况就无法判断，到底make函数构建std::vector时使用的小括号还是大括号，但是通过代码运行可以发现，底层使用的小括号，所以如果是想要使用初始化列表的方式，就应该使用new，而不是通过make
