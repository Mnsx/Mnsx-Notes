## 多线程

### 多进程和多线程

* **多进程并发**

  多进程并发将一个应用程序划分为多个独立的进程（每个进程只有一个线程），这些独立的进程间可以互相通信

  由于操作系统对进程提供了大量的保护机制，以免一个进程修改另一个进程，**使用多进程比使用多线程相对更安全**

  但这也就造成了多进程并发的两个缺点：

  * 在进程间通信，无论使用信号、套接字、还是文件、管道等方式，**其实用要么比较复杂，要么就是速度较慢**
  * **运行多个进程开销很大**，操作系统要分配很多的资源来对这些进程进行管理
  
* **多线程并发**

  多线程并发指的是在同一个进程中执行多个线程

  线程是轻量级的进程，每个线程独立运行不同的指令序列，但是线程不独立拥有资源，依赖于创建他们的进程而存在，**同一个进程的多个线程共享相同的地址空间**，可以访问进程中的大部分数据，这样同一进程内多个线程能够很方便的进行数据共享以及通信

  缺点在于由于缺少系统提供的保护机制，在多线程共享数据及通信时，**需要做更多的工作以保证共享数据段的操作是以预想的操作顺序进行的**

### 创建线程

将函数添加到线程中即可

```c++
// 1.
std::thread t(threadFun); // 函数声明为void threadFun()
t.join();

// 2.
std::thread t(threadFun(100)); // 函数声明为void threadFun(int a)
t.join();

// 3.
std::thread(threadFun, 1).detach(); // 匿名线程，函数声明为void threadFun(int a)
```

### join和detach方式

当线程启动后，一定要在和线程相关联的thread销毁前，确定以何种方式等待线程执行结束

* **detach方式**，启动的线程主动在后台运行，当前的代码继续往下执行，**不等待新线程结束**
* **join方式**，等待启动的线程完成，才会继续往下执行

可以使用`joinable()`判断是join模式还是detach模式

## mutex

mutex头文件主要声明了与互斥量相关联的类，mutex提供了4种互斥类型

| 类型                  | 说明            |
| --------------------- | --------------- |
| mutex                 | 最基本的Mutex类 |
| recursive_mutex       | 递归Mutex类     |
| time_mutex            | 定时Mutex类     |
| recursive_timed_mutex | 定时递归Mutex类 |

`mutex`对象提供了独占所有权的特性，即**不支持递归对对象上锁**，而`recursive_mutex`则支持这一功能

### lock与unlock

mutex常用操作：

* `lock()`：资源上锁
* `unlock()`：解锁资源
* `trylock()`：查看是否上锁，未上锁返回`false`并上锁，其他线程已经上锁返回`true`，**同一个线程已经对它上锁将会产生死锁**

> **死锁**，是指两个或两个以上的进程在执行过程中，**由于竞争资源或者由于彼此通信而造成的一种阻塞的现象**

同一个mutex变量上锁之后，一段时间内，只允许一个线程访问它

```c++
void printBlock(int n, char c) {

    mtx.lock();
    for (int i = 0; i < n; ++i) {

        cout << c;
    }
    cout << endl;
    mtx.unlock();
}

int main() {

    thread t1(printBlock, 50, '$');
    thread t2(printBlock, 50, '*');

    t1.join();
    t2.join();

    return 0;
}
```

如果是不同的mutex变量，因为不涉及到同一资源的竞争，所以可能会出现两个线程交替操作资源，或者另一个线程可以修改共同的资源

```c++
mutex mtx1;
mutex mtx2;
int testNum = 1;

void printBlock1(int n, char c) {

    mtx1.lock();
    for (int i = 0; i < n; ++i) {

        cout << c;
        testNum = 1;
        cout << testNum;
    }
    cout << endl;
    mtx1.unlock();
}

void printBlock2(int n, char c) {

    mtx2.lock();
    for (int i = 0; i < n; ++i) {

        cout << c;
        testNum = 2;
        cout << testNum;
    }
    cout << endl;
    mtx2.unlock();
}

int main() {

    thread t1(printBlock1, 50, '$');
    thread t2(printBlock2, 50, '*');

    t1.join();
    t2.join();

    return 0;
}
```

### lock_gurad

创建`lock_guard`对象时，**它将尝试获取提供给它的互斥锁的所有权**

当控制流离开`lock_guard`对象的作用域时，**`lock_guard`析构并释放互斥量**

* **创建即加锁**，作用域结束**自动析构并解锁**，无需手动资源管理
* **不能中途解锁**，必须等作用域结束才解锁
* **不能复制**

```c++
int i = 0;
mutex mtx;

void safe_increment() {

    const lock_guard<mutex> lock(mutex);
    ++i;
    cout << this_thread::get_id() << i << endl;
    cout << this_thread::get_id() << endl;
    cout << i << endl;

    thread t1(safe_increment);
    thread t2(safe_increment);

    t1.join();
    t2.join();

    cout << i << endl;
}
```

### unique_lock

它具有`lock_guard`的所有功能，同时能够应对更加复杂的锁需求

* **创建时可以不锁定**，在需要时进行锁定
* **可以随时加锁解锁**
* 作用域规则同`lock_guard`，析构时自动释放锁
* 不可复制，**可移动**
* **条件变量需要该类型的锁作为参数**

```c++
struct Box {

    explicit Box(int n) : num(n) {};
    int num;
    mutex mtx;
};

void transfer(Box & from, Box & to, int num) {

    // 默认自动枷锁，defer_lock表示暂时unlock
    unique_lock<mutex> lock1(from.mtx, defer_lock);
    unique_lock<mutex> lock2(to.mtx, defer_lock);
    lock(lock1, lock2);

    from.num -= num;
    to.num += num;

    this_thread::sleep_for(chrono::seconds(1));
}

int main() {

    Box a(100);
    Box b(50);

    thread t1(transfer, ref(a), ref(b), 10);
    thread t2(transfer, ref(b), ref(a), 5);

    t1.join();
    t2.join();

    cout << a.num << endl;
    cout << b.num << endl;

    return 0;
}
```

> `std::ref`用于包装按引用传递的值
>
> `std::cref`用于包装按const引用传递的值

## condition_variable

`condition_variable`有两个`variable`类，一个是`condition_variable`，另一个是`condition_variable_any`

`condition_variable`必须结合`unqie_lock`使用，`condition_variable_any`则可以使用任何的锁

条件变量可以阻塞（`wiat`、`wait_for`、`wait_until`）调用的线程直到使用（`notify_one`、`notify_all`）通知恢复为止

### wait

当线程调用`wait()`后将被阻塞，直到另一个线程调用`notify_*`唤醒当前线程

当线程被阻塞时，该函数会自动调用`lck.unlock()`释放锁，使得其他被阻塞在竞争锁的线程得以继续执行

如果另外的线程调用`notify_*`唤醒了当前线程，那么函数会自动调用`lck.lock()`，使得`lck`状态和之前相同

```c++
mutex mtx;
condition_variable cv;
int target = 0;

void consum(int n) {

    for (int i = 0; i < n; ++i) {

        unique_lock<mutex> lck(mtx);
        cv.wait(lck, [] { return target == 1; });
        cout << target << endl;
        target = 0;
    }
}

int main() {

    thread t1(consum, 10);

    for (int i = 0; i < 10; ++i) {

        while (target == 0) {

            this_thread::yield();
        }
        unique_lock<mutex> lck(mtx);
        target = i + 1;
        cv.notify_one();
    }

    t1.join();

    return 0;
}
```

### wait_for

`wait_for`可以指定一个时间段，在当前线程收到通知或指定的时间`rel_time`超时之前，该线程都会处于阻塞状态

```c++
template <class Rep, class Period>
  cv_status wait_for (unique_lock<mutex>& lck,
                      const chrono::duration<Rep,Period>& rel_time);
```

另外，`wait_for`的重载版本的最后一个参数`pred`表示`wait_for`的预测条件，只有当`pred`条件为`false`时调用才会阻塞当前线程，并且在收到其他线程的通知后只有当`pred`条件为`true`时才会被接触阻塞

```c++
template <class Rep, class Period, class Predicate>
    bool wait_for (unique_lock<mutex>& lck,
         const chrono::duration<Rep,Period>& rel_time, Predicate pred);
```

## 基于任务的设计

想要以异步的方式运行一个函数，可以通过两种方式，一种是基于线程的途径使用 `std::thread`

```c++
int doAsyncWork();
std::thread t(doAsyncWork());
```

或者将函数传递给 `std::async` ，这种策略叫做基于任务

```c++
auto fut = std::async(doAsyncWork);
```

从上述两段代码可以看出，基于任务的方式，能够获取返回值，而通过线程无法获得，这意味着如果在函数中抛出了异常，通过任务实现的方式可以获取到这个异常，而通过线程则只能停止程序（经由调用 `std::terminate` ）

**软件线程是一种有限的资源**，如果试图创建的线程数量多于系统能够提供的数量，就会抛出 `std::system_error` 异常

即使没有用尽线程，还是可能会发生超订的问题，也就是**就绪状态的软件线程超过了硬件线程数量时**，这种情况法僧以后，线程调度器会为软件线程在硬件线程之上分配 CPU 时间片。当一个线程的时间片用完，另一个线程启动时，就会执行**语境切换**，这种语境切换会增加系统的总体线程管理开销，尤其在一个软件线程的本次和下一次被调度器切换到不同的 CPU 内核上的硬件线程时，这种情况下

1. 那个软件线程通常不会命中 CPU 缓存（它们几乎不会包含对于那个软件线程有用的任何数据和指令）
2. CPU 内核运行的新软件线程还会污染CPU缓存上为旧线程所准备的数据

**避免超订问题是困难的，因为软件线程和硬件线程的最佳比例取决于软件线程变成可运行状态的频繁程度**

而使用 `std::async` 正是解决这个问题，它能够对线程进行管理，不需要使用者操心这些问题

```c++
auto fut = std::async(doAsyncWork); // 由标准库的实现者负责线程管理
```

如果申请的软件线程多于系统可以提供的, std::async 被调用时，系统不保证创建一个新的软件线程，而是**允许调度器把指定函数运行在请求结果的线程中**

但是这种策略如果运行在GUI的线程就会可能产生阻塞的问题，因为调度器没法知道那个线程在响应性方面需求很高

这种情况下就应该把 `std:::lanuch::async` 的启动策略传递给 std::async ，这样就能够保证函数确实在另一个线程中执行

但是在以下几种情况，使用线程会更加合适

* **需要访问底层线程实现的 API**

  pthread 的线程库通常会比 C++ 并发 API 提供更多的功能，为了访问底层线程实现的 API ，std::thread 通常会提供 `native_handle` 成员函数，而 std::future 并没有提供

* **有能力有需求优化线程用法**

* **需要实现超越 C++ 并发 API 的线程技术**

## async

使用 std::async 有两种启动策略，它们都有用限定作用的枚举类型 `std::launch` 中的枚举量来表示

* **std::launch::async** 启动策略意为着函数必须以异步方式运行，即在另一个线程之上执行
* **std::launch::deferred** 启动策略意味着函数只会在 std::async 所返回的期值的 get 或 wait 被调用时才会运行，即执行会推迟到一个调用发生的时刻，调用的线程会阻塞到函数运行结束为止

std::async 的默认启动策略是，**采用两者进行或运算的结果**

```c++
auto fut1 = std::async(f);
auto fut2 = std::async(std::launch::async | std::launch::defferred, f);
```

上述两个方式是相同的含义，正是因为这个弹性实现，使得 std::async 与标准库的线程管理组件能够承担线程的创建和销毁、避免超订，以及负载均衡的责任

但是这种默认启动策略在调度上的弹性常会在使用 thread_local 变量时导致混淆，因为这意味着在读写此线程级存储时 ，无法预知会取得哪个线程的局部存储

```c++
using namespace std::literals;

void f() {
    std::this_thread::sleep_for(1s);
}

auto fut = std::async(f);

while (fut.wait_for(100ms) != std::future_status::ready) {
    ...
}
```

默认启动策略就会导致上述的问题，如果 async 是并发执行的，那么就不会有任何问题，但是如果函数被推迟到了调用时运行，因为对任务调用 wait_for 或者 wait_until 不会触发调用函数 ，这意味着循环会一直进行

修正上述问题并不困难，只需要更换校验思路，**校验 std::async 返回的期指，确定任务是否被推迟**，如果被推迟就避免进入超时循环

```c++
auto fut = std::async(f);

if (fut.wait_for(0s) == std::future_status::deferred) {
    // 被推迟了，避免超时循环
} else {
    // ...
}
```

结合上述的问题，以默认启动策略对任务使用 std::async 能正常运作的条件

* 任务不需要与调用 get 或 wait 的线程并发执行
* 读/写哪个线程的 thread_local 变量并没有影响
* 或者可以保证 std::async 返回期值时调用 get 或 wait ，或者可以接收任务可能永远不会执行
* 使用 wait_for 或 wait_until 的代码会将任务被推迟的可能性纳入考量

可以实现 C++11 版本的自动使用 std::launch::async 作为启动策略的工具

```c++
template <typename F, typename... Args>
inline std::future<typename std::result_of<F(Args...)>::type> reallyAsync(F&& f, Args&&... args) {
    
    return std::async(std::launch::async, std::forward<F>(f), std::forward<Args>(args)...);
}
```

## 线程联结

std::thread 类型的对象都处于两种状态之一：可联结和不可联结

可联结的对象对应底层以异步方式已运行或可运行的线程，对应的底层线程处于阻塞或等待调度，则它可联结，对应的底层线程已经运行至结束，则也认为其可联结

而不可联结的 std::thread 类型对象包括

* **默认构造的 std::thread**

  这种对象没有可执行的函数，因此没有对应底层执行线程

* **已移动过的 std::thread**

  移动操作的结果时，一个 std::thread 所对应的底层执行线程被对应到另一个 std::thread

* **已联结的 std::thread**

  联结后，std::thread 类型对象不再对应至已结束运行的底层执行线程

* **已分享的 std::thread**

  分离操作会把 std::thread 类型对象和它对应的底层执行线程之间的连接断开

```c++
constexpr auto tenMillion = 10000000;

bool doWork(std::function<bool(int)> filter, int maxVal = tenMillion) {
    
    std::vector<int> goodVals;
    
    std::thread t([&filter, maxVal, &goolVals] {
        
        for (auto i = 0; i <= maxVal; ++i) {
            
            if (filter(i)) {
                
                goodVals.push_back(i);
            }
        }
    });
    
    auto nh = t.native_handle();
    
    if (conditionsAreSatisfied()) {
        
        t.join();
        performComputation(goodVals);
        return true;
    }
    
    return false;
}
```

上述代码，如果 conditionsAreSatisfied 返回 true ，则正常，但是如果它返回 false 或者抛出异常，那么会在函数末尾调用 std::thread 类型对象的析构函数时，因为它是处于可联结状态，从而导致程序执行停止

这样的情况非常的不合理，但是另外两种明显的选型更加不合理

* **隐式Join**

  在这种情况下，std::thread 的析构函数会等待底层异步执行的线程完成，但是这会导致难以追踪的性能异常，比如 conditionsAreSatisfied 已经返回 fasle 了，但是还在等待线程中工作完成

* **隐式detach**

  在这种情况下，std::thread 的析构函数会分离 std::thread 类型对象和底层执行线程之间的连接，这种情况更加恐怖，当 conditionsAreSatisfied 返回 false 时，函数会退出，那么临时变量 vector 会被销毁，但是底层的线程仍然在执行，这个线程可能随时会访问一个不存在的内存

可以通过自己实现的RAII类型管理到底使用那种策略

```c++
class TrheadRAII {
public:
    enum class DtorAction { join, detach };
    
    ThreadRAII(std::thread&& t, DtorAction a) : action(a), t(std::move(t)) {}
    
    ~ThreadRAII() {
        if (aciton == DtorAction::join) {
            t.join();
        } else {
            t.detach();
        }
    }
    ...
}
```

因为成员变量的生成可能是有依赖性的，所以像上述代码中一样，应该将 thread 放在初始化列表的最后，这也是设计代码时需要考虑的点

## 线程句柄析构函数

因为与被调方关联的对象和与调用方相关联的对象都不是适合为异步执行存储结果，那么只能在外部位置存储，这个位置成为共享状态，**共享状态通常使用堆上的对象来表示，但是类型、接口和实现标准都未指定**

* 指涉到经由 std::aysnc 启动的未推迟任务的共享状态的最后一个期值会保持阻塞，直到该任务结束
* 其他所有期值对象的析构函数只仅仅将期值对象析构就结束了

常规行为是指期值的析构函数仅会析构期值对象，而相对于正常行为的哪个例外，必须满足以下全部条件才会生效

* **期值指涉的共享状态是由于调用 std::async 才创建的**
* **该任务的启动策略是 std::launch::async** 
* **该期值是指涉到该共享状态的最后一个期值**

## 线程间通信的最佳实现

在正常情况下通常是使用 `std::condition_variable` 和 `std::mutex` 配合进行通信，在多个反应任务需要被通知时这确实是一个非常好的方法，但是如果只有一个反应任务，那么这个方法就显得稍微复杂

使用这种方法的第一个问题就是**代码异味**：即使代码能够一时运作，但是某地地方还是感觉不对劲，上述的方式中异味的源头就是使用互斥体，互斥体是**用于控制共享资源访问的**，但是检测和反应任务之间可能根本不需要这种介质

除了这个问题之外还有两个不可忽视的问题：

* **如果检测任务在反应任务调用 wait 之前就通知条件变量了**，则反应任务将失去响应
* **反应任务的 wait 语句无法应对虚假唤醒**

针对上述问题，一个很好的办法就是使用共享的布尔标志位，该标志位的初始值为 false

```c++ 
std::atomic<bool> falg(false);
```

这种方式确实解决了互斥体和虚假唤醒的问题，但是随之而来的问题就是，反应任务的轮询成本

在任务等待标志位被设置的时候，它实质上是应该被阻塞的，但是却任然可以运行，他会一直占用硬件线程，而且每次开始运行以及其时间片结束时，都会产生语境切换的成本

综合下来常见的手法是**结合条件变量和标志位**的设计，但是这总办法还是有一丝异味存在

另一种方法是摆脱条件变量、互斥量和标志位，方法是**让反应任务去等待检测任务设置的期值**

因为发送端是 `std::promise` 类型对象，并且其接收端是期值的通信信道用途不仅仅是调用者和被调用者一种，这种信道可以用于任何需要将信息从一处传输到另一处的场合，对于这个方法而言，**使用它将信息从检测任务传输到响应任务**

检测任务有一个 std::promise 类型对象，即信道的写入端，反应任务有对应的期值，当检测任务发现它正在查询的事件已经发生时，它会设置 std::promise 类型对象，同时反应任务调用 wait 以等待它的期值，这个 wait 方法会阻塞反应任务直到 std::promise 类型对象被设置为止

**因为我们所需要的 std::promise 和期值模板时一种表示没有数据通过信道传输的**，那么类型就是void，因此检测任务将使用 std::promise<void\> ，并且反应任务使用std::future<void\> ，**反应任务可以通过调用 std::promise 的 set_value 方法来了解检测任务何时写入数据**

这个办法解决了大部分的问题，但是还是存在，因为共享状态通常时动态分配的，这种设计就需要考虑，在堆上进行分配和回收的成本

并且 **std::promise 类型对象只能设置一次**，意味着 std::promise 类型对象和期值之间的通信通道时一次性机制

## 原子变量和volatile修饰符

原子变量是多线程并发使用，而volatile是给特殊硬件内存使用，并不能混用

`std::atomic` 是多线程开发的首选，因为它能够保证两件事

* **原子性**：操作不分隔，比如 `count++` 如果是原子的，就不会出现，两个线程同时调用只会加一次的情况
* **禁止指令重排**：这是最关键的，编译器和CPU喜欢乱序执行代码来提速，但是 std::atomic 会建立内存屏障，确保屏障前的操作一定在屏障后之前完成
