# 右值

## move和forward

**`std::move`和`std::forward`都是仅仅执行强制类型转换的函数（函数模板）**，std::move无条件的将实参强制类型转换成右值，而std::forward则仅在特定条件满足时才执行强制类型转换

```c++
template <typename T>
typename remove_reference<T>::type && move(T && param) {
    
    using ReturenType = typename remove_reference<T>::type &&;
    
    return static_cast<ReturenType>(param);
}
```

函数返回值是一个&&部分，但是如果T碰巧是左值引用，那么T&&就成了左值引用，为了避免这个情况，**他将特征`std::remove_reference`应用于T**，保证&&应用在一个非引用类型上

```c++
// C++14
template <typename T>
decltype(auto) move(T && param) {
    
    using ReturenType = remove_reference_t<T> &&;
    return static_cast<ReturenType>(param);
}
```

 因为将对象的值移动通常会改动对象，因此C++不允许常量对象传递到可能改动它们的函数，所以移动构造函数的形参被设置为non-const

在设计代码时，如果想要取得对某个对象执行移动操作的能力，则不应该将其声明为const

std::move不仅不移动任何东西，甚至无法保证其强制类型转换后的对象具有移动能力

std::forward跟std::move相似，但是它仅在特定条件下才实施这样的强制类型转换，std::forward的作用在于**仅当其实参是使用右值完成初始化时，它才会执行向右值类型的强制转换**，如果是左值传入不会做任何改变

## 万能引用和右值引用

右值引用和万能引用都是，T&&，但是万能引用可以绑定右值引用也可以绑定左值引用，甚至是const和non-const等等

**在涉及类别推到时**，T&&就是代表的万能引用，反之则代表的右值引用

如果要使用引用成为万能引用，其涉及类型推导是必要条件，但是不是充分条件，**引用声明的形式必须正确无误才行，并且该形式必须正好形如T&&才行**

```c++
template <typename T>
void f(std::vector<T>&& param); // param是一个右值引用
```

当f被调用时，类型T将会被推导，但是param类型声明不是T&&，而是std::vector<T\>&&，这样param就不可能是万能引用，只能是右值引用

```c++
template <class T, class Allocator = allocator<T>>
class vector {
public:
    void push_back(T&& x);
}
```

上述代码也不是万能引用，因为它并不涉及类型推导，push_back是vector的一部分，如果不存在特定的vector实例，那么这个函数也无从存在，所以当具体类型实例存在时，push_back的声明类型已经被确认

```c++
std::vector<Widget> v;

class vector<Widget, allocator<Widget>> {
public:
    void push_back(Widget&& x);
}
```

声明为`auto&&`类型的变量都是万能引用，因为它涉及类型推导以及都有正确的格式T&&

## 引用规范

**针对右值引用使用std::move，针对万能引用使用std::forward**

**在函数返回局部变量时，不能使用std::move**，因为编译器有一种技术叫做**返回值优化（RVO）**，它会直接在接收返回值的内存位置构造，从而实现零拷贝，如果加上了std::move，反而会强迫编译器执行一次移动操作，并限制了编译器进行RVO的能力，性能反而降低了，**如果返回的是函数的参数且参数是右值引用时，就需要使用std::move**，因为参数不符合RVO的条件

## 避免以万能引用重载

形参为万能引用的函数，是C++中最贪婪的，**它会在局现过程中，和几何任何实参类别都会产生精确匹配**，这就是为什么避免以万能引用作为重载候选者的原因，一旦万能引用成为重载候选，他就会吸引走大批的实参类型

C++重载决议规则中声明**若在函数调用时，一个模板实例化函数和一个非函数模板具有相同的匹配程度，则优先选用常规函数**

如果不选择以万能引用作为重载候选，但是需要针对大多数实参类型实施转发，处理办法如下

* **舍弃重载**

  通过修改函数名称来舍弃重载，将冲突的两个函数改为不同的名称

* **传递const T&类型的形参**

  使用传递左值常量引用类型来代替传递万能引用类型，**因为左值常量可以绑定右值，并且延长这个右值的生命周期**

* **传值**

  这是一种可以提升性能并且不会增加复杂性的方法，把传递的形参从引用类型修改为值类型

* **标签分派**

  如果万能引用仅是形参列表的一部分，该列表中还有其他非万能引用类型的形参的话，那么只要该非万能引用形参的重载版本具备充分差的匹配能力，则它就足以将这个带有万能引用的重载版本排除，**这个思路就是标签分派的基础，而这个用来区分的非万能引用类型就是标签**

* **对接受万能引用的模板施加限制**

  编译器会自动生成复制、移动构造函数，所以标签分派在这种情况下失效

  这种情况下需要使用叫做`std::enable_if`的技法，它能够把含有万能引用部分的函数模板被允许采用的条件砍掉一部分

  默认所有模板都是启用的，但是施加了std::enalbe_if的模板只有在满足指定条件的情况下才会被启用

  ```c++
  class Person {
  public:
      template <typename T, typename = typename std::enalbe_if<condition>::type>
      explicit Person(T&& n);
  }
  ```

  `std::is_same`可以用来判断两个类型是否相同

  `std::decay`可以移除T类型带有的所有引用、const、volatile修饰词

  则上述代码的condition应该是

  ```c++
  !std::is_same<Person, typename std::decay<T>::type>::value
  ```

  还可以使用`std::is_base_of`来判断一个类型是不是另一个类型派生而来，通过使用这个函数，可以实现对Person的派生类加工，导致其也能够符合要求

  ```c++
  // C++14
  class Person {
  public:
      template <typename T, typename = std::enable_if_t<
      	!is::is_base_of<Person, std::decay_t<T>>::value
      >>
      ...
  }
  ```

## 引用折叠

引用折叠的核心大前提是C++不允许引用的引用

```c++
int x = 10;
int & & rx = x; // 不能声明引用的引用
```

但是编译器自己在进行类型推导时，且可以生成引用的引用，当编译器生成引用的引用时，他必须遵守一套规则，将它折叠成一个正常的应用，这个规则就是引用折叠

两种不同的引用组合起来就四种情况，折叠规则总结起来就是：**只要左值引用参数，结果就是左值引用，只有两个右值引用参与才会生成右值引用**

```c++
template <typename t> void func(T&& param);
```

* 传入左值

  ```c++
  int x = 10;
  func(x);
  ```

  因为x为左值，C++规定此时的T被推倒为int&，带入模板param就是`int& &&`触发引用折叠，变成`int&`

* 传入右值

  ```c++
  fun(20);
  ```

  因为20是右值，C++规定此时T会被推导为int，带入模板param类型就变成了`int&&`，没有触发引用折叠

**万能引用的本质只是右值引用配合类型推导加上引用折叠规则产生的巧合**

**引用折叠产生的场景**

* **模板实例化（上述情况最常见）**

* **auto类型推导（和上述逻辑相同）**

* **typedef和using别名声明**

  ```c++
  using LvalueRef = int&;
  LvalueRef&& x = 10; // 折叠为int&（但是左值引用初始化不能绑定右值，仅参考）
  ```

* **decltype推导**

## 慎重使用移动操作

许多string的实现都采用了小型字符串优化（SSO），采用的小型字符串（容量不超过15个字符）会存储在的strd::string对象内的某个缓冲区内，而不是去使用分配在栈上的内存，由于SSO的存在，对于小型字符串移动并不比复制更快

有这几个场景，C++的移动语义并不会带来好吃

* **没有移动操作**

  待移动的对象未能提供移动操作，因此移动请求变成了复制请求

* **移动未能更快**

  待移动的对象虽然有移动操作，但是并不比复制操作更快

* **移动不可用**

  移动本可以发生的语境下了，要求移动操作不可发射异常，但是该操作没有加上noexcept声明

## 完美转发失败情形

因为完美转发的核心引擎是模板类型推导，如果编译器在推导T&&时无法推导出类型，或者推导错误类型，转发机制就会崩溃

* **大括号初始化**

  ```c++
  void process(std::vector<int> v);
  
  process({1, 2, 3});
  
  enqueue(process, {1, 2, 3});
  ```

  上述代码，直接调用不会发生错误，因为参数会隐式转换为vector，而通过完美转发调用就会报错，因为编译器无法推导出具体的类型，如数组，还是std::vector

  解决方法：**借助auto把它变成有类型的变量`auto list = {1, 2, 3};    enqueue(process, list);`**

* **位域（bitfields）变量**

  ```c++
  struct IPv4Header {
      uint32_t version : 4;
      uint32_t IIHL : 4; // 位域：只占4字节
  };
  
  void checkVersion(int v);
  enqueue(checkVersino, header.version); // 报错
  ```

  完美转发的本质是传递引用，但是在计算机底层，内存的最小寻址单位是字节，C++绝对不允许创建一个指向单独几个字节的引用或者指针

  解决办法：**先按值拷贝出来`uint32_t v = header.version;    enqueue(checkVersion, v);`**

* **重载的函数名和模板名**

  如果目标函数需要接收另一个函数作为回调

  ```c++
  void myCallback(int);
  void myCallback(double);
  
  void runTask(void (*cb)(int));
  
  equeue(runTask, myCallback); // 报错
  ```

  编译器在执行enqueue的模板推导时，看到myCallback，会无法理解该选择哪一个

  解决办法：**强制类型转换，明确告诉编译器选择哪一个`static_cast<void(*)(int)>(myCallback)**

* **0或NULL作为空指针**

  如果目标函数想要一个指针`void func(int* p)`，你通过完美转发传入0或NULL，编译器会将他们推导为整型（int），等转发到目标函数时，由于类型不匹配报错

  解决办法：**用于不要使用0或NULL代表空指针，使用nullptr**

* **仅有声明的static const整型变量**

  ```c++
  class Widget {
  public:
      static const int MinSize = 10;
  };
  
  void checkSize(int size);
  enqueue(checkSize, Widget::MinSize); //链接期报错
  ```

  完美转发传递的是引用，而引用的底层通常是通过指针实现，这意味着传入的变量必须在内存中有真实的地址，如果编译器没有MinSize分配地址，代码可以编译通过，但是在链接时找不到符号报错

  解决方法：**在对应的.cpp文件中显示提供定义，或者强制类型转换为右值`static_cast<int>(Widget::MinSize)`**

完美转发受制于C++严苛的类型推导规则——

* 当它遇到没有明确类型的实体（如`{}`、重载函数）时会失败
* 当它遇到无法取地址的尸体（如位域、无定义的常量）时会失败
* 当它遇到类型推导有歧义的实体（如0代替指针）时会失败

## emplace

`emplace_back`时一个被高度推从的性能优化神器，**简单的讲他就是`push_back`的升级版**，核心目的在于**消除不必要的临时对象的创建和拷贝**

### 核心区别

* push_back

  接收一个已经构造好的对象，如果传入的是参数，它会先创建一个临时对象，再把这个对象拷贝（或移动）进容器

* **emplace_back**

  接收构造函数所需的参数，它直接在容器管理的内存空间里就地构造对象

### 实现逻辑

emplace_back的底层实现就是完美转发

```c++
template <class... Args>
void emplace_back(Args&&... args) {
    
    // 使用std::forward完美转发所有参数给内部的构造函数
    allocator.construct(ptr, std::forward<Args>(args)...);
}
```

### 漏洞

* **`explicit` 构造函数的安全隐患**

  emplace_back 会无视 explicit 关键字进行隐式转换

  ```c++
  class Worker {
  public:
      explicit Worker(int id) {}
  };
  
  std::vector<Worker> v;
  v.push_back(10); // 报错，禁止隐式转换
  v.emplace_back(10); //通过
  ```

* **异常安全性和内存泄漏**

  ```c++
  std::vector<std::shared_ptr<T>> v;
  v.emplace_back(new T());
  ```

  如果 vector 在 emplace_back 内部由于扩容失败抛出异常，此时 new T() 申请的内存还没来得及交给 shared_ptr 管理，这就会产生内存泄漏

  而 push_back则是安全的

* **语义清晰度**
